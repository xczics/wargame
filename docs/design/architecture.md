# 架构规划

> 这里放**尚未实现**的架构：以后要加的系统、预留好的接口怎么用、已知的限制和改进方向。已经实现的架构见 `docs/development.md` 第 2 节；玩法以 `docs/design/gameplay.md` 为准。某一项实现后，把它移进 `docs/development.md`，从这里删掉。

## 1. 以后的系统（已预留接口）

### 1.1 不透明科技 / 基金委

- 在首都注册"基金委"建筑（`buildings.define({ kinds: ['capital'], unique: true })`）。点开后可以筛选要资助的**项目**；项目**随机生成**，可能成功也可能失败。
- 每个项目无论成败都会积累"科技树隐藏点数"，提升以后项目的成功率。
- 成功的项目通过 `research.registerNode` 生成科技树之外的新节点（通常只对该玩家可见），再用 `research.grantLevel` 授予等级。
- 项目、点数、概率都由不透明科技插件自己的表来管。英雄可以作为"负责人"提出项目（英雄职务用 `heroes.defineDuty` 注册）。

### 1.2 迷雾

- `terrain.addVisibility` 是迷雾插槽：迷雾插件决定某个玩家能看到哪些格子，地图视图按它过滤。没有迷雾插件时全部可见。

### 1.3 更多通知

- 邮箱（`mail.send`）目前接了战报、被攻击（含流寇）、短缺、秘境冒险、"有望"类道具的结果和 GM 群发。建造完成、科技完成等需要时，由对应插件监听事件后发信（用 `mail.present` 显示为通用报告），不要改邮箱本身。

### 1.4 美术

- 45° 等距视角 + 像素风，见 `docs/design/ui.md` 第 5 节。

### 1.5 区服拆分

- 单个 D1 库约支撑几千人同时在线。更大规模时按"区服"拆分：一个区服一个库；插件只通过 `api.db` 访问数据库，拆分时不用改插件。

### 1.6 NPC 营寨按种子算出、不落库（2.0.0 计划）

用户 2026-10-05："不要1，把3计入2.0.0的计划中。"背景（changelog 247）：铺满全图的 NPC 营寨约 1.23 万座，每座写地块、城池、城区、营寨等级、资源约 5 张表，加上索引约 15.4 万行写入；部署时 `pnpm map:import` 一次写完，超过免费计划每天 10 万行（导入也计入写入，D1 不支持整库拷入，见 D1 定价页"including inserting existing data into a new database"）。

- 营寨按"地块 + 世界种子"确定性地算出（在不在、类型、等级、守军、可抢），和现在播种用的 `seededRandom` 一致；没被碰过的营寨**不存任何行**。
- 只有被攻打、被拔除、被占领的营寨写一行（它和"算出来的样子"的差异）；被拔除的在别处"补回"也改为按种子换位置，而不是写新行。
- 需要的接口：地图占用（`worldMap.occupants` / `window`）能识别"算出来的占用"；`settlements.get` 等能返回未落库的 NPC 城池（只读视图），第一次写它时再落库。
- 好处：导入写入接近 0，地图大小与 D1 额度无关；存储也随实际交战量增长。
- 兼容：已有世界的营寨行照常有效（落库的优先于算出的）；迁移时可以删掉"从没被碰过、和算出的一样"的行。

## 1.5 Cloudflare 计费与缓存（2026-10-05 查官方文档）

用户 2026-10-05："检查一下cloudflare的计费规则，200缓存的内容应该不计入'请求数'吧？"。官方文档（workers/platform/pricing、workers/static-assets/billing-and-limitations）：

- **浏览器缓存命中**（`immutable` / `max-age` 内）：请求不出浏览器，不计任何请求。
- **带 ETag 的重新验证（304）**：请求到达 Worker，**计一次 Worker 请求**（只省流量）。
- **Worker 前的 Cloudflare 缓存（Workers Caching）命中**：按每次请求同价计费，只是不计 CPU。
- **Workers 静态资源**（部署时上传的文件）："Requests to static assets are free and unlimited"，不计 Worker 请求（`run_worker_first` 匹配到的除外）。
- 免费计划每天 10 万次 Worker 请求（UTC 0 点重置）；Worker 发出的子请求不计费。

由此的取舍：

- 带版本号的数据一律 `immutable`（`/api/static/<id>/<版本>`、地形块），每个浏览器每个版本只请求一次。
- `/api/meta` 已改为按版本 `immutable`（1.3.2，changelog 243）：浏览器记住版本号，再次打开从缓存取。以后也可以在构建时生成成静态资源文件（免费）。
- 静态视图以后放进对象存储（服务 `staticStore` 的 R2 实现），R2 桶用自定义域名直接对外时，浏览器直接从 R2 取，不经过 Worker；R2 读操作另计（每月前 1000 万次免费），前面再加 CDN 缓存可以进一步减少。只依赖内容、不依赖 GM 规则的静态视图也可以在构建时生成成静态资源。

## 2. 已知限制与改进方向

- **GM 改规则后的耗尽时刻**：GM 修改规则导致产率变化时，已登记的资源耗尽事件不会重新计算，要等该城下一次执行命令。可以加定时任务兜底。
- **跨实体事件的结算时刻**：别的实体的事件（如军队回城）改动城池产率时，城池在事件**被处理时**结算，而不是事件时刻，误差最多一个清扫周期（约 1 分钟）。要精确可以让时间线支持"一个事件影响多个实体"。
- **防守战报的旧存储**：守方战报已改为邮件，`pvp_reports` 表（`pvp.raid` 仍写入）和 `pvp.defenses` 视图前端不再使用。下个版本可以删除视图，之后停写、再删表（先确认线上不再依赖）。
- **NPC 营地**：被打后没有冷却 / 重生。
- **流寇**：不在地图上显示、不能半路拦截；新手保护只看首都的建立时间（老玩家要等下一次花费后才开始有流寇）。
- **地图生成**：道路网在平面上做三角剖分（不跨地图接缝连路）；公平性只上调过低的区块。
- **没有训练地点的兵种**：`UnitDef.trainedAt` 为空的兵种只能通过 API 训练，界面上没有入口。内容插件定义可训练的兵种时要填写它。
- **运维**：登录接口没有频率限制；过期会话只在读取时失效，不主动清理。
- **前端**：通用控件的数据随视图整份下发，大列表（几百件装备、上千封邮件）没有分页或虚拟滚动；邮箱自己分页。`ui.grid` 每次移动重新请求整个窗口。
