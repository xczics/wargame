# 架构规划

> 这里放**尚未实现**的架构：以后要加的系统、预留好的接口怎么用、已知的限制和改进方向。已经实现的架构见 `docs/development.md` 第 2 节；玩法以 `docs/design/gameplay.md` 为准。某一项实现后，把它移进 `docs/development.md`，从这里删掉。

## 1. 以后的系统（已预留接口）

### 1.1 不透明科技 / 基金委

- 在首都注册"基金委"建筑（`buildings.define({ kinds: ['capital'], unique: true })`）。点开后可以筛选要资助的**项目**；项目**随机生成**，可能成功也可能失败。
- 每个项目无论成败都会积累"科技树隐藏点数"，提升以后项目的成功率。
- 成功的项目通过 `research.registerNode` 生成科技树之外的新节点（通常只对该玩家可见），再用 `research.grantLevel` 授予等级。
- 项目、点数、概率都由不透明科技插件自己的表来管。英雄可以作为"负责人"提出项目（英雄职务用 `heroes.defineDuty` 注册）。

### 1.2 迷雾

- `terrain.addVisibility` 是迷雾插槽：迷雾插件决定某个玩家能看到哪些格子，地图视图按它过滤。没有迷雾插件时全部可见。

### 1.3 更多通知

- 邮箱（`mail.send`）目前接了战报、被攻击（含流寇）、短缺、秘境冒险、"有望"类道具的结果。建造完成、科技完成等需要时，由对应插件监听事件后发信，不要改邮箱本身。

### 1.4 美术

- 45° 等距视角 + 像素风，见 `docs/design/ui.md` 第 5 节。

### 1.5 区服拆分

- 单个 D1 库约支撑几千人同时在线。更大规模时按"区服"拆分：一个区服一个库；插件只通过 `api.db` 访问数据库，拆分时不用改插件。

## 2. 已知限制与改进方向

- **GM 改规则后的耗尽时刻**：GM 修改规则导致产率变化时，已登记的资源耗尽事件不会重新计算，要等该城下一次执行命令。可以加定时任务兜底。
- **跨实体事件的结算时刻**：别的实体的事件（如军队回城）改动城池产率时，城池在事件**被处理时**结算，而不是事件时刻，误差最多一个清扫周期（约 1 分钟）。要精确可以让时间线支持"一个事件影响多个实体"。
- **防守战报的旧存储**：守方战报已改为邮件，`pvp_reports` 表（`pvp.raid` 仍写入）和 `pvp.defenses` 视图前端不再使用。下个版本可以删除视图，之后停写、再删表（先确认线上不再依赖）。
- **NPC 营地**：被打后没有冷却 / 重生。
- **流寇**：不在地图上显示、不能半路拦截；新手保护只看首都的建立时间（老玩家要等下一次花费后才开始有流寇）。
- **地图生成**：道路网在平面上做三角剖分（不跨地图接缝连路）；公平性只上调过低的区块。
- **没有训练地点的兵种**：`UnitDef.trainedAt` 为空的兵种只能通过 API 训练，界面上没有入口。内容插件定义可训练的兵种时要填写它。
- **运维**：登录接口没有频率限制；过期会话只在读取时失效，不主动清理；玩家不能改密码（见 `docs/deployment.md` 第 6 节）。

## 3. 前端插件整合（方向已定；第 1、2 步已实现，见 `docs/development.md` 2.6 与 ui.md 第 3 节）

用户原话："你现在帮我盘一下前端插件数，看能不能尽可能把所有前端插件合并成一个，然后后端插件向前端插件注册显示方式和位置。前端插件把控件尽可能抽象出来以便复用"。

### 3.2 目标：一个前端 + 控件库 + 后端声明

- **一个前端应用**：`web/` 只剩外壳（登录门、顶部 / 底部窄带、页面布局、城池切换、资源条）和一个**控件库**。不再有按玩法分的前端插件。
- **后端声明"显示什么、放在哪"**：✅ 已实现为系统插件 `ui`（`ui.page / block / entry / band / slot / mail / dynamic`，经 meta `ui` 下发）。通用控件接上以后，声明还要能带上**数据来源**：控件读哪个 view、带什么参数、控件自己的配置（`view`、`params`、`props`）。
- **控件库（通用）**：每个控件只认一种数据形状（写在 `src/shared/ui.ts`，两端共用类型）：
  - `cards`：卡片网格（图标、标题、副标题、数量、颜色、角标、点开后显示的表单）——道具、商品、秘境商店、招募候选、存放处……
  - `timers`：带进度条 / 倒计时的列表，每行可带按钮（命令 + 参数）——建造、训练队列、研究、行军、冒险、来袭警报……到点自动刷新（替代各插件各自的 `refreshAt`）。
  - `rows`：键值 / 表格行，可带按钮——驻军、职务、英雄加成、城墙器械……
  - `badge`：一段文字（悬停说明）——官职与声望、未读数。
  - `forms`：现有的服务端表单，原样保留。
  - `report`：通用的"标题 + 键值 + 奖励行"报告（冒险报告、短缺报告可用；分路战况仍是专用控件）。
- **"专用"的可视化也做成可复用的通用控件**（用户 2026-10-02："前端插件可以尽可能收集更多的空间，供后端插件声明。这样第三方加新系统的时候可以复用。比如地图插件，第三方可以引入一个'异世界'副本，在一个更小的网格上，让玩家战斗等。"）。每个控件只认一种数据形状，具体内容全由后端声明，现在的界面只是它们的一个实例：
  - `grid`：任意大小的格子地图（宽高、是否首尾相接、格子底色 / 图块层、标记层、视野、缩放与拖动），点一个格子 → 按 `placement: 'grid:<id>'` 列出可用的命令表单（参数带 x、y）。**世界地图**是 1024×1024、首尾相接、地形底色 + 城池 / 军队标记的一个 `grid`；第三方的"异世界"副本可以声明一张 9×9 的 `grid`，自己的格子、怪物标记和"在此作战"表单，前端不用改一行。
  - `cells`：一组带状态的格子 / 栏位（空、在建、已建、锁定，每格可点开表单）——城区九宫格、建筑栏位、装备部位与饰品一行、阵列的五路都是它。
  - `tree`：分层分支的节点图（节点、前置连线、等级 / 进度、点开表单）——科技树；也可用于技能树、天赋树。
  - `lanes`：多路对比（每路双方的单位、数值、胜负、加成）——分路战况；也可用于其他按路结算的玩法。
  - 只有**GM 后台**（管理界面）保留为单独的代码。
- **第三方自己的前端插件**（用户 2026-10-02："如果第三方认为以上都表达不了的时候，可以开发自己的前端插件。在不改变官方代码的情况下进行扩展。"）：前端插件机制（`defineClientPlugin` + `game.widget(name, 组件)`）**保留为对外的扩展点**。第三方在自己的前端插件里注册控件，在自己的后端插件里用 `ui.page / block / entry / band / slot / mail` 声明它放在哪，官方代码一行不改。为此两端都要能**自动发现**扩展：约定目录 `extensions/<id>/`（`server.ts` 默认导出后端插件、`client.ts` 默认导出前端插件、`data/` 放 CSV），构建时用 `import.meta.glob` 收集，和官方插件一起装配；官方清单 `src/plugins.ts`、`web/plugins.ts` 不用动。
- **view 的形状**：要用通用控件的 view 直接返回控件的数据形状（例如 `shop.store` 返回 `cards`）；或者在 `ctx.ui.block` 里给一个服务端的"整形"函数，把现有 view 转成控件形状——这样已有的 view 不用改，GM 工具和测试照常用原始数据。建议后者。

### 3.3 文案（i18n）也归后端

现在 `locale-zh` 前端插件里有 600 多行**内容**名称（建筑、兵种、道具、官职……），违反"一个插件只管自己"。✅ 已改为每个后端插件在自己目录下带文案表（`data/i18n.csv`：`key,zh-CN`），系统插件 `i18n` 汇总后随 `/api/meta` 下发；前端只保留外壳自己的文案。新增内容（第三方插件）不用碰前端就能有中文。

### 3.4 分步迁移（每步都可上线、可回退）

1. ✅ **文案下沉**（changelog 84）：系统插件 `i18n`（没有改内核）；把 `locale-zh` 和各前端插件里的 `game.messages` 按归属搬进各后端插件的 `data/i18n.csv`。界面不变。
2. ✅ **布局声明**（changelog 83）：系统插件 `ui`（没有改内核），先引用**现有的** Vue 组件名；前端外壳按 meta 摆放，前端插件的 `setup` 变成纯"组件注册"。
3. **通用控件**（进行中：✅ 声明可带 `props`（`view` / `params` / 控件配置，前端自动订阅 `view`）；✅ `ui.badge`，替换了官职与声望；✅ `ui.cards` + `ui.filters`，替换了聚宝阁；✅ `ui.timers`，替换了兵营入口的训练队列；✅ `ui.rows`，城墙入口（`ui.timers` + `ui.rows`）替换了城防面板）：实现 `cards` / `timers` / `rows` / `badge` / `report`，逐个把可声明化的界面换掉（顺序：prestige、shop、inventory、troops、siege、armies、mail、realms、heroes、equipment 的商店与存放处、research 的研究所），每换一个删掉对应组件。
4. **可视化控件通用化**：把世界地图改写成 `grid`（世界地图的数据由 `world-map` / `terrain` / `settlements` / `armies` 声明），城区九宫格和装备栏改成 `cells`，科技树改成 `tree`，分路战况改成 `lanes`；每做完一个，在测试里用一个小的假插件（例如 5×5 的"异世界"网格）证明第三方能复用。
5. **收尾**：官方控件库放在 `web/widgets/`（官方界面不再按玩法分前端插件）；`defineClientPlugin` 保留给第三方；加上 `extensions/` 自动发现（两端），示例插件 `examples/watchtower` 挪成一个扩展；开发文档、开发指南同步（示例里加一个用 `grid` 的小副本，和一个自带前端控件的扩展）。

预计：官方的前端插件 21 → 0（一个外壳 + 约 10 个通用控件 + GM 后台），代码量减少约三分之一；新玩法插件多数情况下只写后端，连新的地图玩法也是；通用控件不够时，第三方写自己的前端插件，放进 `extensions/` 即可。

### 3.5 用户的决定（2026-10-02）

1. 方向：可视化也做成通用控件（`grid` / `cells` / `tree` / `lanes`），只有 GM 后台单独保留。
2. 文案下沉到各后端插件（"同意"）。
3. 时机："按前两步 -> 清数据库 -> 后两步来做"：先做 3.4 的第 1、2 步（文案下沉、布局声明），然后 M1 全新存档，再做第 3–5 步（通用控件、可视化控件通用化、收尾）。
