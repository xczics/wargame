# 架构规划

> 这里放**尚未实现**的架构：以后要加的系统、预留好的接口怎么用、已知的限制和改进方向。已经实现的架构见 `docs/development.md` 第 2 节；玩法以 `docs/design/gameplay.md` 为准。某一项实现后，把它移进 `docs/development.md`，从这里删掉。

## 1. 以后的系统（已预留接口）

### 1.1 不透明科技 / 双清观（1.4 计划）

玩法见 gameplay.md 第 14 节（用户 2026-10-18 给出设计）。原来"在这座建筑里随机生成项目"的构想改为：驻守研究所的英雄提出申请书，玩家在首都的双清观里批准。建筑 id 为 `shuangqing-temple`。

#### 插件划分（一切皆插件）

- **`opaque-research`（新系统插件）**：256 维隐藏值、分组与门槛、申请书、项目、点数分配、函评成功率、加成。它不知道有哪些资源、哪座建筑、哪个职务，这些由接线插件告诉它：
  - `opaqueResearch.defineBonus({ id, stat, direction: 'increase' | 'decrease', name })`：登记可选的加成项。GM 规则把每一组指到其中一项；
  - `opaqueResearch.setProposers(duty)`：哪个英雄职务的英雄会提出申请书；
  - `opaqueResearch.setCostReference(fn)`：丙级的花费和用时从哪里来；
  - 同时进行的项目数是一个 stat（`opaque-research.concurrent`，由本插件 `stats.define`），由别的插件 `stats.contribute`；
  - 已解锁的最高项目级别也是一个 stat（`opaque-research.tier`，0 = 一级都没解锁），同样由别的插件给。
- **`starter-opaque-research`（新内容 / 接线插件）**：
  - 首都建筑"双清观"（`buildings.define`，`kinds: ['capital']`，`unique`，策划表 1–7 级，8 级起每级 ×1.27，15 级约为宫殿 20 级的 10 倍，见玩法 14.3）：用 `buildings.addGate` 要求首都研究所 20 级、宫殿 15 级以上；每级给 `opaque-research.concurrent` 加 1；到规定等级（暂按 1 / 5 / 10 / 15 级，规则 `starter-opaque-research.unlocks`）给 `opaque-research.tier` 加到丙 / 乙 / 甲 / 重大；
  - 加成项清单（维持费、各资源产量、建造 / 训练 / 科研的费用或时间……）及默认的分组；
  - 指定"驻守研究所"为提出申请书的职务；
  - 丙级花费参照（透明科技的某一项某一级）；
  - 申请书和函评的句子（`data/texts.csv`，分段、中英文）。
- **别的插件要补的服务**（没有就加，都是通用能力）：
  - `heroes`：职务锁的钩子（主持项目期间不能改职务），以及给经验；
  - `research`：查询某一项某一级的花费和用时（不经过减免）；
  - `shop`：花元宝。

#### 数据（D1）

- `opaque_research_values`：每个玩家一行，存 256 个值和派生的"各组已越过的门槛数"。加成每次同步都要读，而只在项目完成时才变，所以按"常读少变的派生数据存成一行"处理，测试比对"存的"和"现算"一致。没有任何隐藏值的玩家不落行，读的时候尽早返回。
- `opaque_research_heroes`：每名被授予过项目或驳回过申请的英雄一行，存被授予过的最高级别、本季是否已驳回（存被驳回的季序号）。申请书本身不存（见下）。
- `opaque_research_projects`：进行中的项目，存英雄、级别、承诺的目标、批准时定下的偏移和点数、花费、开始和完成时间。完成后删掉这一行。

#### 时间线

- **项目完成**：批准时排完成事件（实体 `hero:<id>`，要加 `timeline.addOwnerResolver`）；处理时分配点数、更新隐藏值和派生数（版本号加一），给英雄经验，解除职务锁。

#### 申请书：看的时候现算，不写表

- 季序号 = ⌊UTC 时间 ÷ 这一级的季长⌋（丙 1 天、乙 2 天、甲 4 天、重大 7 天，GM 规则）。
- 申请书由"英雄 id + 季序号 + 版本号"作种子，按当前隐藏值和在研项目现算。版本号存在 `opaque_research_values` 那一行里，每次项目完成（隐藏值变）或批准（在研项目变）都加一。选目标时按规避系数降分：对每个在研项目连乘 (1 − 深度 × e^(−d² ÷ 2σ²))，d 是到它执行中心的环上距离，暂按深度 0.5、σ 3 格（GM 规则），只降分不排除。256 维 × 在研项目数，每次现算也只是几千次乘法。级别、目标、是否承诺、成功率、句子的种子都由它决定。同一季、版本号没变时，每次算出来都一样；项目完成或批准了新项目就自然改写。
- 所以申请书没有任何写入，也不需要定时事件；换季只是种子变了。驳回时写一行（记下被驳回的季序号），这一季不再显示这名英雄的申请书。
- 视图的 `stamp` = 季序号 + 版本号 + 驳回记录，没变就不重算、不重发。

#### 计算

- **都按闭式算**：选目标（遍历 256 维找离门槛最近、可能越过的那一维）、成功率（点数在浮动范围内均匀分布时，冲刺部分越过门槛的概率，可以直接算出来）、填平（窗口只有 7 维，排序后注水）都是常数级的计算，不逐点循环。
- **随机数**：用项目或申请书的种子（`seededRandom`），保证命令重试时结果一致。偏移在批准时由正态分布抽出（Box–Muller，两次均匀随机数），四舍五入并限制在 ±2 格。

#### 前端

- **不变的**：申请书和函评的句子、加成项清单、门槛序列，做成静态视图，按版本缓存。
- **会变的**：玩家视图只发申请书的参数（种子、级别、组、是否承诺、成功率、英雄）、进行中的项目、各组的加成，带 `stamp`。
- **申请书的正文由浏览器拼**（服务端不渲染文字，"声明的是数据和画法"）：
  - 句子表 `starter-opaque-research/data/texts.csv`：`section,when,weight,en,zh-CN`。段落有研究背景、研究内容、研究方法、研究基础、函评；`when` 是条件，如 `progress=near`、`attr=学识`、`rate=high`、`promise=no`，可以写几个；变量有 `{hero}`、`{bonus}`、`{dim}`、`{rate}`；
  - 条件标签由服务端随申请书一起下发，都是按状态算出来的：`progress`（目标离下一门槛近 / 中 / 远）、`lead`（领先 / 落后周围）、`attr`（英雄最突出的属性）、`tier`、`promise`、`history`（以前主持过几次）、`rate`（成功率高 / 中 / 低）；
  - 浏览器每段先筛出满足条件的句子，再用申请书的种子按权重挑一到两句，同一份里不重复；
  - 函评报告的格式固定：评审人代号（如"函评专家丙"）、按成功率档位挑的评语、最后一行"综合评估：预计突破概率 xx%"；
  - 维度代号用"64 卦 × 4"（如"乾·初"），对照表放在静态视图里；
  - 文风（用户 2026-10-18 选定）：古代口吻说现代基金申请的套话。
- **界面**：双清观的入口里列出所有申请书（英雄、级别、费用、时长、成功率），点开看全文和函评，批准或驳回；下面是进行中的项目。科技页加一块"不透明科技"，列各组的加成。

#### 命令

- `opaque-research.approve { hero, season, version }`，服务端检查：
  - 客户端看到的季序号和版本号与现在一致（不一致就报"申请书已更新"，客户端刷新）；服务端按同一个种子重算申请书，以它为准；
  - 英雄还在驻守研究所、没在主持项目、本季没被驳回；
  - 逐级授予条件满足，这一级已被双清观解锁；
  - 首都有双清观，同时进行的项目没超过上限；
  - 资源和元宝够。

  然后扣首都的资源和元宝（不可取消、不受减免），锁英雄职务，定下偏移和点数，排完成事件。

- `opaque-research.reject { hero, season }`：记下本季已驳回（一行）。
- 测试：
  - 双清观的建造条件（研究所 20 级、宫殿 15 级）；逐级授予（没授予过丙级的高等级英雄只能申请丙级）、双清观没解锁的级别不会被申请也不能批准、同时进行数随双清观等级加 1、没有双清观时不能批准；
  - 资源或元宝不足被拒、花费不受减免、主持期间不能改职务、驻守加成保留；
  - 完成后点数分配符合"冲刺 + 填平"、环首尾相接（第 256 维的邻居是第 1 维）、越过门槛后加成增加、派生数和现算一致；
  - 申请季：同一季、版本号不变时申请书不变，换季、项目完成或批准了新项目就改写；规避会让新申请书避开在研项目的范围，但项目再多也总能选出目标；各级的季长正确，驳回后本季不再出现，过期的季序号或版本号批准被拒；
  - 成功率和模拟结果相符（大量种子统计）、没有承诺时是固定值；偏移的分布符合设定的标准差（大量种子统计），且在批准时就已定下；
  - 命令重试时结果一致、两个批准命令并行只成功一次。

#### 步骤

1. `heroes` 的职务锁和给经验、`research` 的花费查询、`shop` 的花元宝（缺哪个补哪个）。
2. `opaque-research`：表、隐藏值和派生数、选目标、成功率、分配、加成、申请季（现算的申请书）、批准 / 驳回、完成事件、玩家视图和静态视图。
3. `starter-opaque-research`：双清观、加成项清单、提出申请书的职务、花费参照、句子表。
4. 前端：双清观入口、申请书全文（浏览器拼句子）、科技页的"不透明科技"块。
5. `pnpm check`、`pnpm smoke`；核对没有隐藏值的玩家不多读、同步只多一个带戳的小视图。

### 1.6 地图数据：地形只放 R2，营寨按规则算出（1.4 计划）

用户 2026-10-05 把"营寨按种子算出、不落库"列进计划，2026-10-17 提前到 1.4，并定下："那就只有地形仅R2, 营寨走规则计算。"

**为什么**（changelog 247）：铺满全图的营寨约 1.23 万座，每座写地块、城池、城区、营寨等级、资源约 5 张表，加上索引，导入时约 15.4 万行写入，超过免费计划每天 10 万行（导入也计入写入）。现在分钟级的播种限速只能避开单次调用最多 50 条语句的限制，省不了按天累计的额度。改完后：营寨导入时写入 0 行，地形导入时 D1 写入 0 行，拔除一座营寨约 1 行。

**原则**：不变的世界数据放进文件或由规则算出；会变的状态放 D1；D1 只记"和算出来的不一样"的地方。

#### A. 地形：一个带版本号的文件，只放 R2

- **格式**：整张地图一个文本文件，每格一个字符（地形代码，对照表仍在 meta 的 `terrains`），按行从 `minY` 开始。1024×1024 约 1 MB，压缩后约 150 KB（实测现有地图 gzip 160 KB、brotli 140 KB）。存成压缩好的文件（`Content-Encoding`），键为 `terrain/<版本>`。
- **版本**：沿用 D1 的 `terrain_version`（一行），只当作指向当前文件的指针。
- **写入**：
  - `pnpm map:import` 直接写 R2：线上加 `--remote`，本地 / Docker 写进 `.data/local` 里模拟的 R2；
  - GM 的 `terrain.paint` 改为"生成新文件、换版本"：先把新版本写进 R2，再执行一条命令，把受影响的城池结算到此刻（原来的 `settleOn`）并在同一个提交里把版本号加一。新旧文件同时保留，切换是原子的；旧版本以后由后台任务清理。
- **服务端**：模块级缓存 `版本 → 文件内容`，每个 isolate 每个版本读一次 R2，之后 `terrain.of / at / mix` 都查内存。城区的产量加成要用地形，结算、后台任务、只读视图都会调用，这些场合没有客户端，所以服务端必须自己持有地形。原来按块读 D1 的 `loadChunk` 去掉。
- **浏览器**：地图控件的地面改为一次取整张文件，长期缓存。线上从 R2 的公开域名取（新的环境变量，如 `MAP_BASE_URL`），不经过 Worker；没有配置公开域名时（本地、Docker），经由 Worker 的路由 `/api/terrain/<版本>` 从 R2 读出返回，同样 `immutable`。
- **绑定**：`wrangler.jsonc` 加一个 R2 绑定（如 `FILES`），地形、静态视图、拼图图片共用这一个桶，按键的前缀分（`terrain/`、`static/`、`puzzles/`）；之后跑 `pnpm cf-typegen`。Docker 里模拟的 R2 和 D1 一起存在 `/data/local`，`pnpm data:backup` 整目录复制，自然包含在内。
- **已有世界**：新增 `pnpm map:export`，把 D1 的 `terrain_chunks` 导出成文件写进 R2，部署 1.4 之前执行一次。`terrain_chunks` 在 1.4 停用，下个版本删表。

#### B. 营寨：按规则算出，D1 只记例外

- **规则函数**（放在 `src/shared/`，前后端共用一份代码）：`营寨(块, 槽位) = f(世界种子, 密度规则, 等级权重)`。每块营寨数 = `perBlock ± spread`，每个槽位的位置、类型（`fortressShare`）、等级都由种子哈希决定，和现在播种用的 `seededRandom` 同一套办法。守军、栅栏、首领、可抢资源本来就是按等级现算的，不变。
- **参数下发**：种子、密度、等级权重做成一个静态视图（`npc-camps.layout`，带版本号）。GM 改密度或权重时版本变，浏览器和服务端一起换成新布局。
- **身份**：规则营寨的 id 由块和槽位决定，例如 `npc:<bx>,<by>,<槽>`。军队目标、时间线实体 `settlement:<id>`、引擎锁、战报邮件都只需要一个稳定的字符串，不需要那一行真的存在。
- **例外表**（新表，如 `npc_camps_state`，按块存）：只记两件事，被攻打的时间（`raided_at`）和已被移除（被拔除，或被 GM 放营寨覆盖）。只有这样的槽位才有行，只是查看不写任何行。已移除的规则营寨永远不再出现。
- **规则营寨什么时候"不存在"**（不写任何行，判断时现算）：
  1. **落在首都的九宫格里**：以首都内城为中心的 3×3（内城加第一圈 8 格：外城 1–8 座和新手营寨的位置）之内，规则营寨一律不存在。首都是系统放的，玩家没得选，所以首都紧挨着的 8 格只会有新手营寨和 GM 手放的营寨，不会出现要等很久才打得掉的高级营寨。第二圈（靠道具开的外城）不受保护，那里的规则营寨照常存在，要建外城就先拔除那一座（玩家可以对首都 5×5 以内的营寨发起拔除行军，一次去掉一座，见玩法 2.7）。分城不受保护：位置是玩家自己选的，选在营寨旁边，要建外城就得先打赢拔除（用户 2026-10-17："如果头铁非要在营寨边上建分城，就该它们亲自拔除了，才能建外城啊"）。
     - 首都建成的那一刻，周围的规则营寨就消失了，所以选址仍然只要求 3×3 空着；
     - GM 调密度换成新布局时，落进首都九宫格的也自动不存在，不用另外判断；落在分城附近的照常存在，和玩家选址时遇到营寨一样处理。
  2. **格子已被真实占用**（`world_map_tiles` 里有玩家城池、GM 放的营寨、新手营寨）：真实的优先。这条用来兜底已有世界的迁移和 GM 手动操作。
  3. 例外表里记着它已被移除。

  判断方法：先由函数算出这一格有没有营寨（绝大多数格子没有，到此为止）；有的话，再查一次这一格周围 3×3 里有没有首都（一次范围查询，要给 `settlements_settlements` 加 `(kind, x, y)` 索引），以及这一块的例外表（一行）。地图视野、占地、选址这些路径本来就要读这一片，基本不多花。

- **占地检查**（玩家筑城、选首都位置、开外城）：
  1. 照旧查 `world_map_tiles` 并插入，玩家之间的冲突由坐标主键挡下；GM 放的营寨、新手营寨也在这张表里，同一次查询就能发现；
  2. 用规则函数算这一格有没有规则营寨，有的话按上面的三条确认它此刻在不在。绝大多数格子不多读一行。
- **需要的扩展点**（加在系统插件的服务里，不改内核）：
  - `worldMap`：登记"虚拟占用者"，`occupants / window / claim` 合并真实和虚拟两种来源；
  - `settlements`：登记"虚拟城池来源"，`get / getMany / nearby` 能返回没落库的 NPC 城池。

  `npc-camps` 去登记这两样，系统插件本身不认识营寨。

- **攻打**：写一行例外（`raided_at`），回满规则（`npc-camps.refillHours`）照旧。两支部队同时打同一座营寨，靠 `settlement:<id>` 的锁保护。

### 1.7 静态视图放 R2，meta 在构建时生成（1.4 计划）

用户 2026-10-17："静态视图和地形块进 R2，加上 meta 在构建时生成，我也觉得可以做。"

- **静态视图**：`staticStore` 服务已经预留（`src/runtime/statics.ts`），实现 R2 版本，键为 `static/<id>/<版本>`。现在每个 isolate 冷启动都要重新生成一遍；放进 R2 后，每个版本全局只生成一次（两个 isolate 同时生成，写入的内容相同，不冲突）。线上浏览器从公开域名直接取；本地和 Docker 照旧走 `/api/static/<id>/<版本>`，由 Worker 从 R2 读出。
- **meta**：meta 只取决于部署的代码和内容，不依赖 GM 规则，所以在构建时生成成静态资源文件（如 `meta/<版本>.json`），版本号打进前端代码。Workers 的静态资源不计请求、不收费；首次访问时多出的 `/api/meta` 和 `/api/meta/<版本>` 两次请求都没了。

### 1.8 拼图碎片（1.4 计划）

玩法见 gameplay.md 第 13 节，界面见 ui.md 第 4 节。这里是实现。

#### 插件划分（一切皆插件）

- **`puzzles`（新系统插件）**：拼图定义、玩家持有的碎片、重复碎片换资源、兑换。图片存 R2；掉落借用 `loot`；奖励类型由别的插件登记。它不知道秘境、营寨、资源、英雄是什么。
- **`starter-puzzles`（新内容 / 接线插件）**：登记奖励类型（资源、道具、装备、军队、随机女英雄、GM 指定配置的英雄、随机奖励池），各自调用拥有者的服务（`resources`、`items`、`equipment`、`troops`、`heroes`、`loot`）；把拼图界面放进听曲楼的入口和道具页的"拼图"类别。
- **`loot` 的通用扩展**：
  - **掉落地点目录**：拥有掉落池的插件用 `loot.describeSites(pool, tree, siteOf)` 登记一棵树（例如 秘境 → 任务 → 怪物组；营寨 → 类型 → 等级；流寇 → 等级），以及"这次掉落发生在树上哪个位置"。GM 后台据此画出可勾选的树，"所有秘境"就是勾整棵子树。
  - **独立概率的掉落项**：除了按权重抽，掉落项可以写 `chance`（0–1）：每次在符合条件的地点结算时独立判定一次，不挤占池里别的东西。
  - **由数据驱动的掉落项**：`loot.addSource(pool, load)`，掉落项来自运行时数据（GM 配的拼图），而不只是 setup 时写死的。按版本缓存，见下面的"性能"。
- **各掉落池的拥有者**（`realms`、`npc-camps`、`bandits`、`pvp`）各自登记地点目录。
- **`heroes`**：提供"直接授予一名英雄"的服务方法（属性逐项指定、留空的随机，可指定性别），复用"GM 放置候选"的生成逻辑；英雄已满时报错，兑换就不成立。

#### 数据

- **D1**：
  - `puzzles_defs`：编号、名字（GM 输入，显示用 `literal`）、网格边长 n、状态（草稿 / 上线 / 停止掉落 / 下架）、图片的键、掉落规则、重复碎片换的资源（可按块另设）、兑换上限、奖励（JSON）、版本；
  - `puzzles_pieces`：玩家、拼图、块号，主键 `(player_id, puzzle_id, piece)`。有这一行就是有这一块，不记数量；
  - `puzzles_claims`：玩家、拼图、已兑换次数，`CHECK (count >= 0)`，主键 `(player_id, puzzle_id)`。
- **R2**：每张拼图一个文件（`puzzles/<编号>/<版本>.webp`），长期缓存。

#### 图片：一张原图，处理都在浏览器里

- 用户 2026-10-17："客户端做就好，一次性加载整张图，浏览器做裁减。"Worker 不处理图片（免费计划每次请求的 CPU 上限是 10 ms，也处理不了）。
- GM 上传：在 GM 后台页面里用 canvas 拖框裁成正方形、缩放到上限（如 1536×1536）、编码成 WebP，一个请求经 GM 路由（`accounts.requireGM`，写审计日志）放进 R2。服务端只检查格式、大小和尺寸。
- 换图会生成新版本的文件，旧文件留给还没刷新的浏览器，以后由后台任务清理。网格边长只是一个数字，只在草稿状态下能改（改了就和玩家已有的碎片对不上）。

#### 显示

- 浏览器一次加载整张原图：线上从 R2 的公开域名取，本地 / Docker 经由 Worker 路由读 R2；都带版本号，长期缓存。
- 前端新增通用控件（如 `ui.mosaic`）：n×n 网格，每格用 CSS 裁出原图对应的那一块；已收集的格子正常显示，没收集到的格子加模糊、压暗（CSS `filter`），就是"虚化蒙版"。听曲楼的拼图界面和道具页的缩略图都用它。

#### 掉落

- 每条掉落规则：碎片（一块或多块）、地点（树上的若干节点）、价值、概率。上线的拼图才参与掉落。
- 结算时：池的拥有者照常调 `loot.roll`；`loot` 按这次的地点找出适用的拼图规则，逐条按 `chance` 判定，掉到的经 `puzzles` 的 `give` 发放：玩家还没有这一块就写进 `puzzles_pieces`（一行）；已经有了，或这张图已达兑换上限，就按设定发资源（经 `starter-puzzles` 登记的资源奖励类型，`puzzles` 不认识资源）。都列进战报。
- **"价值"**（用户 2026-10-17 确认）：沿用掉落算法里的价值（玩法 9.5）：掉到的碎片，价值计入这次掉落的最低总价值，同一次里别的东西相应少一些。

#### 性能（按 AGENTS.md 的原则）

- **不变的**：拼图目录（名字、边长、图片地址、奖励说明、哪里掉、兑换上限）做成静态视图，按版本长期缓存。GM 每次改拼图时递增规则版本（和 GM 改规则共用 `gm_config_version`），所以不多一次读取。
- **服务端的掉落索引**：模块级缓存 `版本 → (地点 → 适用的规则)`，每次结算只查自己的地点，没有适用规则就立刻返回。大多数战斗不会多读一行。
- **会变的**：玩家视图只发"每张图收集了哪些块、已兑换几次"，带 `stamp`（碎片的变动），没变就不发。只读这个玩家的行（`WHERE player_id = ?`）。
- **写入**：掉一块新碎片写一行；重复碎片只有资源的写入；兑换删掉这张图的碎片行、更新一行兑换次数，加上奖励本身的写入。

#### 兑换

- 命令 `puzzles.claim { puzzle }`：服务端检查这张图已上线或停止掉落、玩家每块都有、兑换次数没到上限，再逐项发奖（各奖励类型的 `give`，同一个提交里），清空这张图的碎片，兑换次数加一。浏览器的"兑换"按钮只决定显示与否。
- 测试：集齐才能兑换（缺一块被拒）、到上限后被拒、兑换后碎片清空可以重新收集、并行兑换只成功一次、英雄已满时兑换被拒且碎片不变、重复碎片和到上限后的碎片换成设定的资源、掉落只在勾选的地点发生、草稿状态的拼图不掉落、GM 路由无权限时返回 401 / 403。

#### 步骤

1. `loot` 的三项扩展，以及四个掉落池登记地点目录（带测试）。
2. `puzzles`：表、GM 路由（上传、编辑、上下线、审计）、掉落、兑换、玩家视图和静态视图。
3. `heroes` 的"直接授予英雄"；`starter-puzzles` 登记各奖励类型。
4. 前端：GM 后台的拼图编辑页（上传裁切、网格、掉落设置和一键选项、奖励）；通用控件 `ui.mosaic`；道具页的"拼图"类别；听曲楼入口里的拼图界面。
5. `pnpm check`、`pnpm smoke`，用 `pnpm requests` 和 `perf.spec.ts` 核对：没有拼图掉落的战斗不多读，玩家同步只多一个带戳的小视图。

## 1.5 Cloudflare 计费与缓存（2026-10-05 查官方文档）

用户 2026-10-05："检查一下cloudflare的计费规则，200缓存的内容应该不计入'请求数'吧？"。官方文档（workers/platform/pricing、workers/static-assets/billing-and-limitations）：

- **浏览器缓存命中**（`immutable` / `max-age` 内）：请求不出浏览器，不计任何请求。
- **带 ETag 的重新验证（304）**：请求到达 Worker，**计一次 Worker 请求**（只省流量）。
- **Worker 前的 Cloudflare 缓存（Workers Caching）命中**：按每次请求同价计费，只是不计 CPU。
- **Workers 静态资源**（部署时上传的文件）："Requests to static assets are free and unlimited"，不计 Worker 请求（`run_worker_first` 匹配到的除外）。
- 免费计划每天 10 万次 Worker 请求（UTC 0 点重置）；Worker 发出的子请求不计费。

由此的取舍：

- 带版本号的数据一律 `immutable`（`/api/static/<id>/<版本>`、地形块），每个浏览器每个版本只请求一次。
- `/api/meta` 已改为按版本 `immutable`（1.3.2，changelog 243）：浏览器记住版本号，再次打开从缓存取。以后也可以在构建时生成成静态资源文件（免费）。
- 静态视图以后放进对象存储（服务 `staticStore` 的 R2 实现），R2 桶用自定义域名直接对外时，浏览器直接从 R2 取，不经过 Worker；R2 读操作另计（每月前 1000 万次免费），前面再加 CDN 缓存可以进一步减少。只依赖内容、不依赖 GM 规则的静态视图也可以在构建时生成成静态资源。

## 2. 已知限制与改进方向

- **GM 改规则后的耗尽时刻**：GM 修改规则导致产率变化时，已登记的资源耗尽事件不会重新计算，要等该城下一次执行命令。可以加定时任务兜底。
- **跨实体事件的结算时刻**：别的实体的事件（如军队回城）改动城池产率时，城池在事件**被处理时**结算，而不是事件时刻，误差最多一个清扫周期（约 1 分钟）。要精确可以让时间线支持"一个事件影响多个实体"。
- **流寇**：不在地图上显示、不能半路拦截；新手保护只看首都的建立时间（老玩家要等下一次花费后才开始有流寇）。
- **地图生成**：道路网在平面上做三角剖分（不跨地图接缝连路）；公平性只上调过低的区块。
- **没有训练地点的兵种**：`UnitDef.trainedAt` 为空的兵种只能通过 API 训练，界面上没有入口。内容插件定义可训练的兵种时要填写它。
- **运维**：登录接口没有频率限制。
- **前端**：通用控件的数据随视图整份下发，大列表（几百件装备、上千封邮件）没有分页或虚拟滚动；邮箱自己分页。`ui.grid` 每次移动重新请求整个窗口。
