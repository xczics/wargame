# 复盘：2026-09-30 → 10-25

用户 2026-10-05："等你都做完了之后，总结一下今天的坑，然后盘一下哪些是本可以在游戏设计一开始就考虑好的（而不是现在修），另外有没有哪些关键能力应该进核心/共享函数库。"；10-25："早该写了，放在1.6.0之前。"

写给以后接手的人和 agent：先看第 2 节（一开始就该定的事），新功能照着做。括号里的数字是 changelog 编号，可以去 `docs/changelogs/` 核对；性能的细节在 `docs/workers-performance.md`，这里不重复。

规模：测试 57（9-30）→ 148（1.0.0）→ 382（10-25）；插件 57 个，前端插件 35 个。

## 1. 坑：经过、返工几轮、根因

### 1.1 数据与显示分离（至少 5 轮，返工最大）

- **10-02（83–113）**：21 个前端插件合并成"后端声明 + 通用控件"，但声明的是**画好的结果**：服务端每次请求拼卡片、行、按钮、句子再下发。这一步在制造债。
- **10-05（205–246）**：地图每次同步重算每格的颜色和名字。用户："这些难道不是前端的计算任务吗？"；"出现这种问题说明声明接口没设计好。"加了静态视图和变动戳，城池页拆成静态目录 + 玩家栏位（"服务端不算！前端算，服务端只做校验！"）。
- **10-20（324–330）**：小助手挂机后线上约 30% 的请求因超过 10 ms 被掐。用户："前端早就让你数据-显示分离了，一直拖着，越拖问题越严重"；"预渲染永远只在部署或GM变规则之后做，而且只通过R2分发！"写成 AGENTS 硬原则，常驻测试禁止数据视图里出现带变量的句子。被掐比例约 30% → 0。
- **10-21（360、390）**：表单的 `prepare` 也只发数据（"训练部队和遣散部队的表单还没有进R2，还是workers渲染的？"），道具页表单 38 KB → 16 KB。
- **10-24（465–474）**：装备、英雄卡片、冒险属性、战报、奖励描述改成浏览器拼；10-25（486）军队页的兵种数值也由浏览器按静态目录算。
- **根因**：一开始的控件契约是"服务端给成品"，不是"数据 + 画法"；结构化文字（UiText）又把组句子固定在了服务端。**教训**：拼文字不是 CPU 大头（兵营条目 3.7 → 3.3 ms，360），分离的价值在体积、可缓存和架构。

### 1.2 多语言（3 次大改）

- 9-30 用英文原文当键、按句型反查，撞名不断（"City"/"Overview"、宽泛句型抢先匹配）；84 把文案下沉到各插件；134 改成"插件 id.key + 英文 + 中文"（"一次性搞定，不给后面留尾巴"）；151 结构化 UiText，删掉反查（用户："这次i18n的改动说明前期做好架构设计是很有必要的"）。
- 之后还有十来次零星泄漏：把键当字符串传、缺译（143、169、296、331、380），翻译表写在 TS 里（245），模板字符串拼句子（480）。
- **根因**：一开始没有键的归属和结构，事后靠 `scripts/check.mjs` 和完整性测试兜底。

### 1.3 性能：按"常驻服务"的习惯设计（约 8 轮，详见 workers-performance.md）

- 10-03（200）：命令平均 6 s。一次状态请求查 `heroes.get` 1749 次，后台每分钟扫 6900 行，资源池每次结算写满全部行。
- 10-03（202）：撞上每次调用 50 条语句的上限（播种 1600 条 → 60）。
- 10-05（204–217）：命令后把数据重读一遍、每次新建 `Intl.NumberFormat`（15.7 ms）、科技加成每查一项扫整表；原则这时才写进 AGENTS（"保证agents每次添加功能时，都能从最开始就按照设计"）。
- 两次撤回：服务端每次比对视图指纹（235，"'重复比较'的任务不能每次在服务端做"）、meta 的 304（243，304 也计请求）。
- 10-19（292、301–306）：主键只用到一半的范围查询（地图 1017 → 351 行）、规则每个请求重新解析（"这些难道之前从来没有预烘焙过吗？"）、戳太粗；Worker 离数据库太远，一次同步 3–4.6 s，改 placement 后 0.15–0.4 s。
- 10-20（317–323）：定时任务没活也装配（"定时任务难道不就是闹钟吗？"）、meta 版本号每个实例现算。
- 10-21（400–421）：读取打包、CSV 构建时预编译、没变的同步只读一次、命令预读。
- 10-22/24（440–462）：实测线上几乎一直解释执行，**CPU ≈ 执行的代码量**（441）；快速通道、扁平视图；memo 复制父级的平方级问题（446）；定时任务 83 → 3 ms（453）。
- **根因**：照"长寿命服务"的心智设计：依赖实例内存缓存、按请求装配、在读路径上按规则现算。官方限制（10 ms CPU、50 条语句、100 个参数、304 计请求）当时就查得到，却没有从第一天起按它设计。

### 1.4 读路径代替写路径（4 次）

军队到达只在只读视图里算、战报发不出来（⑮）；本地 cron 两份（141）；停服后补算留下孤儿记录（210）；短行军试过"懒结算"被否（350，"数据库里这样做，前端还是'装装样子'"）；到期事件每次同步在内存里重算（420 才有 `timeline.settle`）。**根因**：允许"在视图里处理事件、写入丢弃"，结果每个只读请求都在重复算。

### 1.5 缓存与派生值失效（至少 7 次）

GM 改了规则掉落权重不生效（68）；静态视图不随内容变化重烘焙（283、313）；部署没升版本号，旧的 `npc-camps.levels` 让地图白屏（451）；之后每次部署全量重烘焙又太危险（452，改成按指纹）；派生值的形状变了而 salt 没变，旧行被当新值读回（459）；memo 继承了不相干的表，派生值每次建造都过期（461）；表单被同步清空三次（㊶、167、213）。**根因**："依赖了什么"全靠手写维护：版本、salt、`tables` / `ignore` 列表、`content` 标记各写各的，没有单一来源。

### 1.6 常规路径与快速通道、以及各写一套

建造、练兵、研究、进攻各手抄一份快速通道（442–447），审计时才把纯逻辑合并（481–483）。更早：资源"最多 X"只在一个表单算过（296，"举一反三复查。是不是该复用的没复用，各写一套了？"）、兵营加速没上卡片（319）；10-02 的评审发现 107 处手写参数校验、5 份"没有这位英雄"、13 处手拼人名（142）。

### 1.7 插件边界

research 的表单写死 gold（W1）、基础产出写在 player-settlements（D）、npc-camps 直接查 settlements 的表（200）、一处插件间运行时导入和六处写死 `'capital'`（475）、bench 读别人的表（484）。现在还有 9 个插件里 21 处 `tables` / `ignore` 列表写着别的插件的表名，以及 `settlements.ownerSql` / `tilesSql` 这类 SQL 片段（1.6.0 第 3 步处理）。

### 1.8 兼容、迁移与数据形状

迁移合并了三次（129、139/140、223；"保持sql干净,这个版本只留一个sql。"）；写了没人读的表（268）；旧数据的含义被改写：百分比当固定值（58）、0 当成"没写"（339，"指定0,价值就真是0, 默认应为null"）、奖励存的形状和表单不一致（307）；升级时要按旧规则结算，规则快照放进 R2（294）。

### 1.9 发布、安全、流程

提前发布 1.0.0 被撤回（92–93，"我让你都完成之后再发布"）；发布说明只链接 changelog（163）；1.4.0 撤回重发（291）；CI 超时没出镜像（156、249）；令牌过期迁移晚了（458）。公开的 R2 域名能下到不透明科技的分组（300）；登录到 10-20 都没有限流（315–316）；部署信息进过公开仓库（用户随后清理了历史）。文档与代码对不上约 70 处（470），changelog 里残留过合并冲突标记（295）。

### 1.10 不稳定的测试（10 次以上）

统计性断言（97、120）、真实时钟（156、187）、超时（156、249、324、485）、随机掉落（281）、**共享地图上别的测试留下的城**（297、477、485）。**根因**：所有测试共用一个世界，"每个测试一个新玩家"隔离不了地图上的东西。

### 1.11 小助手（3 轮）

第一版挂机引发 503（322 → 324）；"用前端已有的数据，不要找服务端额外请求数据"（371）；"说了多少遍，小助手只能用前端数据！"（448，复盘见 workers-performance.md 2.1）；之后陆续删掉 `/api/data`（455）、`troops.overview`（480）、`npc-camps.garrisons`（486）。

### 1.12 本地工具与数值

冒烟的临时目录积到 1.9 GB（261，"这个程序差点把我硬盘给写坏了"）；数值多次被用户否（产量比花费高一个数量级、冒险每天约 800 样掉落、流寇约 30 倍兵力，250–290），短程模拟工具直到 10-05 才有。

## 2. 本可以一开始就定好的

| 主题       | 第一天就该定的                                                                                                                                      | 能否预见                                                                              |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 数据与显示 | 视图只发实体和规则算出的数；不变的内容做成带版本的静态目录；控件契约是"数据 + 画法"；显示判断在浏览器、服务端照样校验；常驻测试禁止数据视图出现句子 | 能（AGENTS 一开始就要求前后端分离）                                                   |
| 多语言     | 命名空间键 + 结构化文字，不用原文当键                                                                                                               | 能（业界常规）                                                                        |
| 性能       | 按官方限制设计：每页查询预算测试、批量查询（`IN` ≤ 90）、计算放在写的时候、meta 和 CSV 构建时烘焙、后台任务先探测再装配、视图带变动戳               | 能；但"线上几乎一直解释执行、实例只活约 8 个请求、计时器在纯计算里不走"只有实测才知道 |
| 读写语义   | 只读请求不处理事件；写的时候结算；到点由客户端闹钟或 cron 提交一次                                                                                  | 基本能                                                                                |
| 失效       | 每份缓存或派生值的依赖只声明一次；每次构建一个构建号、静态视图按指纹重烘焙；派生值形状版本是一个常量                                                | 能                                                                                    |
| 双路径     | 命令写成声明（读什么、检查什么、写什么、调哪些钩子），快速通道由它生成                                                                              | 形状能定；哪条命令是热点要上线才知道                                                  |
| 插件边界   | 表注册 + 给别人用的读法，不许写别人的表名和 SQL 片段                                                                                                | 能                                                                                    |
| 兼容       | GM 覆盖值、奖励配置、派生值带版本的 schema；区分 null 和 0；一个版本一个基线迁移；每张表先问"谁读它"                                                | 能                                                                                    |
| 发布与安全 | 发布清单（范围、说明、CI 余量、令牌）；默认登录限流；公开桶只放可公开的东西；部署信息不进仓库                                                       | 能                                                                                    |
| 测试       | 每个测试分配独立的地图区域；随机数和时钟都注入                                                                                                      | 能                                                                                    |
| 数值       | 一开始就有经济模型和短程模拟                                                                                                                        | 部分；手感偏好要用户试玩才知道                                                        |

预见不了的：用户后来加的玩法（小助手挂机的负载形态、不透明科技、拼图）、Workers 线上的执行特性、手机走 http 时没有安全上下文。

## 4. 给以后的检查清单（新功能动手前）

1. 这块界面的数据，哪些不变（进静态视图 / meta）、哪些会变（进带戳的数据视图）？服务端有没有拼任何文字？
2. 每次同步会跑多少条语句、读写多少行？有没有逐个查？过滤有没有索引？
3. 随时间变的数，是"存值 + 时间、读时闭式算"，还是在读路径里处理事件？
4. 缓存或派生值依赖哪些表、哪些规则、什么形状？形状变了版本号在哪里改？
5. 有没有写别的插件的表名、内容 id？要的东西有没有拥有者的服务或读法？
6. 文字是不是本插件的键、写了英文和中文？
7. 测试会不会被共享地图上别人的东西影响？有没有用真实时钟或不注入的随机数？
8. 小助手要的东西，是不是页面本来就取的数据？
