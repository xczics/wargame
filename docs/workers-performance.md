# Workers 性能：踩过的坑与尝试

写给以后在 Cloudflare Workers（免费计划）上开发本项目的人和 agent。规则性的约定在 AGENTS.md"性能原则"和"数据与显示彻底分离"，实现细节在 `docs/development.md`；这里记**为什么**：线上实测到的事实、试过的办法和结果、用户提出的优化方向。新的优化做完，在第 3 节补一行，数字写线上实测的。

## 1. 先知道的环境事实

- **免费计划每次请求 10 ms CPU，线上真的会掐**：超了不是每次都掐（每个实例有一点弹性，偶尔超出可以），但持续超就返回 503（GraphQL 里 `status = exceededResources`）。2026-10-20 小助手挂机后，约三成请求被掐。
- **CPU 不含等待**：等 D1、R2、fetch 的时间不算；但 **D1 客户端在 Worker 里打包请求、解析结果**（每条语句、每一行都要建对象）是算的。一次同步十几条查询，这部分就不小。
- **实例很短命**：线上平均每个实例只处理约 8 个请求（按 `engine_versions` 每个实例读一次的次数估算：约 290 次对应约 2,400 个请求）。所以：
  - 大多数代码跑在**没被 V8 优化**的状态，本地预热后的数字要乘几倍看（本地命令约 5–10 ms，线上冷实例 30–180 ms）；
  - **实例内存里的缓存基本没用**，"第一次算、之后复用"最多复用几次；
  - **每个实例一次的工作**（装配插件、解析数据表、算 meta 版本）大约摊到每 8 个请求上一次，不能忽略。
- **线上的 CPU ≈ 这次请求在解释器里执行了多少代码**（2026-10-22 用测量地址实测，`src/plugins/bench`）：同一条升级命令对线上快速连发 40 次，CPU 从 51 ms 降到 7–10 ms（连发 10–20 次后 V8 才把它优化好）；而正常游戏几分钟一条命令，同一段代码在一个实例里很少跑到这么多次，所以**几乎一直是解释执行**。同样的读写和算术写成几十行的手写版，第一次就只要 2–3 ms。由此：
  - D1 客户端、纯计算、空请求，线上和本地差不多（D1 每多一次调用线上约 +0.5 ms，批量里多几条语句几乎不加）；差距全在"层层调用的大量代码"上；
  - 本地剖析若在同一实例上连跑几十次，量到的是优化后的速度，会严重偏乐观；本地要按"每个请求都在没优化的代码上跑"来量；
  - 省 CPU 的办法是**减少热路径实际执行的代码量**（扁平的实现、预先算好的表），而不是优化 D1 调用或算术。
  - 实例其实比"约 8 个请求"活得长：测量时 72 个请求只有 4 个落在新实例上（每轮之间停 2 分钟）；冷启动不是主因，热实例上执行的代码太多才是。
- **在 Worker 里量不了自己的 CPU**：计时器只在 I/O 之后前进（防侧信道），`performance.now()` 在纯计算里不动（线上实测：空转 2000 万步，计时器读数为 0；本地 workerd 会走）。
- **R2 用量很小**：静态视图按版本缓存在浏览器里，每人每个版本只读一次（10 月前三周：存储 9.6 MB、A 类 259 次、B 类 1,159 次）。

## 2. 踩过的坑

| 坑                                                     | 后果                                                                                                       | 结论                                                                     |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| macOS 没有 `timeout` 命令                              | `timeout 600 wrangler tail …` 直接失败，两轮"监听"什么都没抓到                                             | 用 `perl -e 'alarm 600; exec @ARGV' pnpm exec wrangler tail …`           |
| `wrangler tail` 只看得到 URL                           | 命令的类型看不见；曾把地图页的出兵误认成"道具页"（两页都带 `items.owned`）                                 | 按页面各自的视图组合认页面，不确定就说不确定                             |
| 官方 CPU 剖析接口（`/workers/.../profile`）            | 结果大部分是"垃圾回收 / 空闲 / fetch 等待"，只采一个实例，常常采不到目标请求                               | 不能用来找 CPU 大头；只看出"每个请求都读一次用量暂停标记"                |
| 以为"服务端拼文字"是 CPU 大头                          | 数据与显示分离把响应体积砍掉一大截，但兵营条目只从 3.7 降到 3.3 ms（本地）                                 | 拼文字不是大头；分离的价值在体积、可缓存和架构，不在 CPU                 |
| 读路径"在内存里先算、下条命令再落库"（短行军的懒结算） | 每个只读请求都要重算一遍，实例不留内存                                                                     | 改成写的时候算完（出兵命令当场结算），前端演出过程                       |
| 每次切页面都同步                                       | 来回点几页就是十几个请求，每个都要查戳                                                                     | 前端大对象里有、60 秒内取过的直接用（changelog 392）                     |
| 定时任务没活也装配上下文                               | 没人玩时每 10 分钟一次 20–35 ms，单次任务装配 4 次                                                         | 先判断有没有活，没活一次都不装配（changelog 317）                        |
| meta 版本号每个实例现算                                | 每个新实例的第一次请求序列化约 470 KB 再算 SHA-256                                                         | 构建时算好写进包里（changelog 318）                                      |
| 为算产量读整张地图文件                                 | 每个冷实例读一次大文件                                                                                     | 只给建了城的格子按城池存一行（changelog 323）                            |
| 观测（observability）怀疑耗 CPU                        | 关掉约 45 分钟对照：中位低约 10–20%，和开着时的波动重叠                                                    | 不算决定性，已重新打开                                                   |
| 每个请求读一次"用量暂停"标记                           | 多一次 D1 往返                                                                                             | 进行中：按分钟缓存（2026-10-21 优化轮）                                  |
| 每页都有的小视图顺手调了"全套"函数                     | `troops.due`（只要练兵完成时间）调用 `garrisonInfo`，每页把每个兵种的费用、用时、加成、闸门全算一遍        | 按调用次数找（`pnpm sync:counts`），只调用需要的那部分（changelog 446）  |
| 确定性的重计算放在视图里每次重做                       | 不透明科技的研究申请每次首访科技页都搜一遍 256 维（约 1.2 万条语句）                                       | 结果只取决于赛季和表里的数据：存成派生值（changelog 446）                |
| 部署没升版本号，静态视图没重新烘焙                     | 清单按 `package.json` 的版本号判断；10-24 部署后沿用了旧的 `npc-camps.levels`（缺新字段），地图页白屏      | 每次构建一个构建号（版本 + 提交 + 时间，changelog 451）                  |
| 为小助手留着专用的服务端视图（`settlements.nearby`）   | 每座出发城一个请求，服务端为它现算规则营寨、等级、补满时间；挪营寨到浏览器时还把它当"需要服务端判断"留下了 | 小助手只用前端数据：改成浏览器里算的视图（复盘见 2.1 节，changelog 448） |
| 引擎每建一个 memo 都复制父级读过的全部 memo            | 地图页一个视图建几百个 memo，复制是平方级（约 2900 条语句）                                                | 只记父级当时的前缀，算戳时再展开（changelog 446）                        |

### 2.1 复盘：小助手向服务端额外要数据（2026-10-22，changelog 448）

- **经过**：1.5.1 起小助手打营寨用服务端视图 `settlements.nearby`（每座出发城一个，带 `x / y / r / npc`）：服务端读窗口、算规则营寨是否立着、再经 `settlements.addNearbyInfo` 补等级和补满时间。它是只为小助手存在的视图。changelog 447 把地图的规则营寨挪进浏览器时，只改了地图，还在汇报里写"小助手和 `settlements.nearby` 仍在服务端算虚拟营寨，它们要据此做判断"。用户："说了多少遍，小助手只能用前端数据！"
- **原因**：把"小助手需要某个判断"当成"服务端要替它算"的理由；没有回头核对设计里早就定下的"小助手是前端秘书……服务器不为它做任何额外的事"（gameplay.md 第 15 节、AGENTS.md"数据与显示分离"）。改一类数据的来源时只改了眼前的消费者，没有把所有消费者（地图、侧栏、小助手、测试）列一遍。
- **改法**：`settlements.nearby` 改成浏览器里算的视图（`web/plugins/settlement/views.ts`，读 `world-map.window` 的数据：城池插件给存着的 NPC 城池，营寨的前端部件按规则补上规则营寨和存储营寨的等级、补满时间，扩展点 `settlements.nearby`）；小助手用 `game.compute(视图, [参数…])` 一次请求取齐各出发城的数据、在浏览器里算。服务端的 `settlements.nearby` 和 `addNearbyInfo` 删掉。
- **以后**：(1) 小助手要的东西只能来自页面本来就取的数据视图和静态视图，在浏览器里用共享代码算；不为它新增、也不为它保留服务端视图或参数。(2) 把一类数据挪到浏览器时，先 `grep` 出它的所有消费者（视图 id、服务方法、测试），一起迁。(3) 汇报里出现"某某仍在服务端算"时，先对照设计原则，不对就当场改，不要当成既定事实交代。

## 4. 怎么量

- **按版本的分位数**：GraphQL `workersInvocationsAdaptive`，按 `scriptName` 过滤，维度 `datetimeFifteenMinutes`、`status`、`scriptVersion`，取 `cpuTimeP50 / P90 / P99`（微秒）。用 wrangler 登录的 OAuth 令牌即可。每次部署是新版本，前后对比就按版本分组。
- **逐个请求**：`wrangler tail -c wrangler.production.jsonc --env production --format json`，每条有 `cpuTime`、`wallTime`、URL、`outcome`；按 URL 里的 `views` 认页面。
- **本地**：`pnpm smoke --keep` 起临时服务，`pnpm profile <地址>` 看各页 CPU 和响应大小；测试里可以逐个算视图、数查询（`test/game/perf.spec.ts`）。本地数字偏乐观（热 JIT、快 CPU），只用来比前后。
- 部署后的第一批请求要重新生成静态视图（`pnpm statics:refresh` 之后尤其明显），量的时候避开或单独看。
- **按调用次数找"不该跑的代码"**（changelog 446）：`pnpm build` 后 `pnpm sync:counts <smoke 数据目录> [--top=N] [--page=页名]`。给打好的 Worker 插上 istanbul 计数器（workerd 的调试接口没有 V8 的精确覆盖率），每页的首访同步发两次、数第二次：按函数的调用次数、按源码行执行的语句数、按模块合计。线上代码基本解释执行，CPU 约等于执行的代码量，所以语句数是个好用的代理；跑完自动还原打包文件。

### 4.1 按阶段量：bench 插件（changelog 440）

Worker 量不了自己的 CPU，所以一个地址只做一件事，线上用 `wrangler tail` 给每个请求的 `cpuTime` 对比。插件 `src/plugins/bench`，变量 `BENCH` 为 `"1"` 时才有（否则 404，和不存在的地址一样）；都要登录，只读本玩家的行，**不写任何东西**（要写的地方换成 `WHERE 0` 的空 UPDATE，参数个数一样）。

| 地址（`/api/_bench/…`）                   | 量的是                                                                                                                                      |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `timers?n=`                               | 忙循环 n 步前后 `performance.now()` / `Date.now()` 的差，和一次 D1 读之后的差：看计时器在纯计算里走不走（线上应为 0，本地会走）             |
| `noop`                                    | 什么都不做：任何请求的底价（路由、闸门、会话一次 D1）                                                                                       |
| `d1?n=&mode=seq\|batch\|pack`             | n 条最小的 SELECT：每条一次调用 / 一个 batch / 同时发出由打包合成 batch；看每次 D1 调用、每条语句的客户端 CPU                               |
| `assemble[?rules=1]`                      | 请求里 `createKernel`（新实例装配插件的代价；线上它在模块加载时做，不算进请求），`rules=1` 再读 GM 覆盖值并把全部规则算一遍（新实例第一次） |
| `upgrade`                                 | 读上一版本的规则文件（约 1.5 MB）并解析：部署后每个池第一次被碰时、每个实例一次                                                             |
| `sync?<和 /api/state 一样的参数>`         | 和 `/api/state` 同样的工作（会话 + 规则 + 记录一起读、算视图、静态视图版本）                                                                |
| `target`                                  | 给下面两个用的建造参数（本玩家等级最低、没在建的建筑）                                                                                      |
| `raw/buildings.construct`（POST）         | 手写的升级：同样的表一次 batch 读、共享的费用公式、按存的产率结算、同样的写换成空 UPDATE 一次 batch；没有内核、引擎、memo、钩子、stat       |
| `real/<命令>[?views=…]`（POST，载荷为体） | 真实命令经 `executeCommand`，写换成空 UPDATE（`dry.ts`，在打包层之下，D1 收到的调用和语句数不变），带 `views` 时再按 `/api/command` 算视图  |

每个回答带 `isolate: { id, served }`（这个实例处理过几个 `/api` 请求，1 = 新实例的第一个）和 `wallMs`。

**本地**：`pnpm smoke --keep`（停掉它）后 `pnpm bench:local <数据目录> [轮数=3] [热请求数=3] [--only=标签前缀]`：每个地址都作为一个新服务的第一个请求（冷），再发几次（热），V8 剖析的自用时间分成 V8 本身（`(program)`：编译、解析）、GC、运行时的 JS（D1 客户端、请求管道）、内核、我们的代码、bench 自己。

**线上**（用户自己操作，部署信息不进仓库）：

1. 在 `wrangler.production.jsonc` 的 production 环境 `vars` 里加 `"BENCH": "1"`，`pnpm run deploy`。
2. 浏览器登录一个有首都的玩家，开发者工具里复制 cookie `wg_session` 的值，存成文件（如 `~/bench-cookie.txt`，内容 `wg_session=…` 或只有值）。
3. 一个终端：`perl -e 'alarm 3600; exec @ARGV' pnpm exec wrangler tail -c wrangler.production.jsonc --env production --format json > ~/bench-tail.json`。
4. 另一个终端：`pnpm bench:online https://<域名> ~/bench-cookie.txt 6`（默认每轮之间停 120 秒让实例换新，`--pause=` / `--gap=` 可调；先用浏览器记下各页的状态请求，日志写到临时目录，结束时打印路径）。
5. 跑完停掉 tail，`pnpm bench:tail ~/bench-tail.json <日志路径>`：按标签列 CPU 中位 / p90、墙钟中位，以及"新实例的第一个请求 / 之后的"各自的中位。
6. 把 `BENCH` 改回 `"0"`（或删掉）再部署。

## 5. 由此得到的设计原则

1. **读的路径只读表**：视图返回存好的行，能让 SQLite 拼好 JSON 原样转发就不解析；不在读的时候按规则现算。
2. **计算放在写的时候**：命令、到点事件、后台任务、GM 改规则时算好派生值写进表。
3. **随时间变的数交给浏览器**：存"结算值 + 结算时间 + 速率"，浏览器按同一份共享公式插值。
4. **不变的只发一次**：内容、规则推出来的东西做成静态视图经 R2，浏览器按版本缓存。
5. **每个实例一次的工作要当成每几个请求一次**：能在构建时做的就在构建时做（meta 版本、数据表），不能的就按需、只做这次请求用到的。
6. **不要指望实例内存缓存**：它最多复用几个请求。
7. **前端少发请求**：前端大对象里有、还新鲜的就不问服务端；要变的东西靠命令的回答、到点闹钟和低频同步。
8. **量了再说**：用线上按版本的分位数判断，不凭本地数字或猜测下结论。
9. **合法命令走快速通道，非法命令由浏览器拦下**（用户 2026-10-22："尽量让所有'合法命令'都能直接快速通道化，然后让前端检查拦截导致会失败的命令。后面测试时可以多检测'非法命令'，这样不断完善前端拦截。"）：命令的扁平实现（`Command.flat`）覆盖会成功的完整情况；会失败的（资源、额度、队列、闸门……）由浏览器按同样的数据先拦下，按钮不可用并说明原因；服务端照样校验。到了服务端还被拒的命令记一行 `[refused] <命令> <代码>`（`http-api`），线上监听据此补前端拦截。
