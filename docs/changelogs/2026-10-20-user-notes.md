# 2026-10-20 用户留言与优化

- ✅ 317 **定时任务没活时不装配**（用户 2026-10-20："我的天，装配那么多次干啥"；"在不变时，应该一次都不装配"；"定时任务难道不就是闹钟吗？为什么要重复一次闹钟机制？不改接口直接由定时插件调度不好吗？"）。
  - 线上：没人玩时每 10 分钟一次的定时任务 CPU 中位 20–35 ms（免费计划 10 ms）。本地预热后只要 2.7 ms：线上的 cron 几乎每次落在新实例上，四个任务各自装配上下文（核对规则版本、首次解析 GM 覆盖值、记录版本），碰到的代码都要现编译。
  - 改法（不改任务接口，各任务内部先判断再装配）：
    - `timeline.sweep`：先查有没有到期事件（`due_at` 的索引，一条小查询），没有就返回；
    - `npc-camps.upkeep`：先查有没有待补的营寨，再装配；
    - `settlements.topUpSlots`：状态行改存 `{ mark, sizes }`，`mark` = 规则版本 + 代码版本；没变就只读这一行和版本号；版本变了但格子数没变，只更新标记、不扫描（旧格式的行按"没有"处理，下一次核对一遍）；
    - `realms.sites`：新表 `realms_task_state`（迁移 `0026`），据点补满后记下标记，之后同上（以前补满的记录存在实例内存里，cron 换实例就丢，于是每次都数一遍）；
    - `usage-guard.check`：检查时把下次检查时间存进状态（`usage.nextAt`），没到点不读规则；
    - `accounts.sessions`、`items.pity`：清理改为每小时一次。
  - 内核：`Kernel.build`（`createKernel(plugins, { build })`：应用版本 + 各插件版本；静态视图的烘焙改用它）、`rulesVersion(kernel, env)`（只读规则版本号）。`docs/development.md` 的 `ctx.tasks.add` 一行写明写法。
  - 结果：新实例空闲时只有 6 条小查询，不读规则、不装配（`test/offline.spec.ts` 新测试断言）；线上另有用量保护的两次状态读取。部署后看 GraphQL 的按小时 CPU。
