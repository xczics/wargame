# 2026-10-22 用户留言与调整

- ✅ 440 **按阶段量 CPU：bench 插件与线上对照脚本**（用户："在本地给代码运行的各个阶段打时间戳（代码装配、模块导入、读写表、逻辑运算等），看看分别占了多少ms。然后线上测试，看看部分哪个差异最大。"；"选一个命令，把他要读写的表和逻辑单独提取出来，在一个干净文件里，把任务复现出来，然后用独立的url调用它，测它的时间，和目前版本的时间，对比差多少。"）。背景：1.5.2 线上命令中位约 100 ms、首次打开一页 14–47 ms，本地新实例只有 11–13 ms 和 2–8 ms。
  - **计时器**：Worker 里量不了自己的 CPU（线上计时器只在 I/O 后前进），所以"打时间戳"改成**一个地址只做一个阶段**，线上用 `wrangler tail` 给每个请求的 `cpuTime` 对比。`/api/_bench/timers` 先验证：本地 workerd 里计时器**会走**（忙循环 2000 万步：`performance.now()` 差 90 ms、`Date.now()` 差 90 ms），所以本地可以打时间戳；线上待量（预计为 0）。
  - 新插件 `bench`（`src/plugins/bench`，只有路由，变量 `BENCH` 为 `"1"` 时才有，`wrangler.jsonc` 默认 `"0"`；都要登录、只读本玩家的行、不写）：`timers`、`noop`、`d1?n=&mode=seq|batch|pack`、`assemble[?rules=1]`、`upgrade`、`sync?…`（与 `/api/state` 同样的工作）、`target`、`raw/buildings.construct`（`raw-construct.ts`：手写的升级，同样的表一次 batch 读、共享费用公式、按存的产率结算、写换成 `WHERE 0` 的空 UPDATE；没有内核 / 引擎 / memo / 钩子 / stat）、`real/<命令>`（真实命令经 `executeCommand`，`dry.ts` 在打包层之下把每条写换成参数相同的空 UPDATE，D1 收到的调用数、语句数不变，什么都不改）。每个回答带 `isolate: { id, served }`（一个计数闸门数这个实例处理过几个 `/api` 请求）。
  - 脚本：`pnpm bench:local <数据目录> [轮数] [热请求数]`（每个地址作为新服务的第一个请求 + 之后几次，V8 剖析按 V8 本身 / GC / 运行时 JS / 内核 / 我们的代码分）；`pnpm bench:online <地址> <cookie 文件> [轮数]`（线上，配 `wrangler tail`）；`pnpm bench:tail <tail 输出> [日志]`（按标签列 CPU 中位 / p90，按 `_n` 对上日志后分"新实例第一个 / 之后"）。`profile:cold` 的起服务、剖析器代码挪进 `scripts/lib/preview.mjs` 共用；请求清单 `scripts/lib/bench-plan.mjs`。用法见 workers-performance.md 4.1 节。
  - **本地结果**（smoke 的测试账号，3 个新服务的中位，ms CPU；冷 = 新服务的第一个请求，热 = 之后 3 个）：

    | 阶段                                         | 冷              | 热              | 冷里的大头                       |
    | -------------------------------------------- | --------------- | --------------- | -------------------------------- |
    | 空请求（路由 + 会话一次 D1）                 | 7.2             | 2.1             | 运行时 JS 5.0（第一次 D1 调用）  |
    | D1：1 条 / 10 条逐条                         | 9.8 / 13.3      | 2.3 / 5.2       | 每次调用热约 0.3 ms、冷约 0.4 ms |
    | D1：10 条一个 batch / 打包 / 40 条一个 batch | 8.4 / 8.3 / 8.6 | 2.1 / 2.3 / 2.8 | 一个 batch 里多几条几乎不加      |
    | 装配内核（请求里 `createKernel`）            | 14.4            | 8.7             | 插件 setup 4.4、运行时 4.2       |
    | 装配 + 全部规则（3 条 GM 覆盖）              | 21.3            | 15.1            | 规则默认值和解析 +6              |
    | 同步（8 页，`sync` 与 `/api/state` 相同）    | 16–28           | 6–10            | 运行时 JS 5–11、我们的代码 4–8   |
    | 升级：手写（raw）                            | 11.5            | 3.3             | 运行时 6.8（两次 D1 调用）       |
    | 升级：真实命令（dry run）                    | 21.2            | 7.0             | V8 编译 9.9                      |
    | 升级 + 城池页视图                            | 33.4            | 11.8            | 运行时 13.5、我们的代码 9.7      |

    结论（本地）：手写版和真实命令只差约 2 倍（热 3.3 vs 7.0、冷 11.5 vs 21.2），框架开销不是 10 倍差距的来源；冷实例的额外 5–15 ms 主要是第一次调用的编译（V8 `(program)`）和运行时 JS；D1 每次调用的客户端开销约 0.3 ms，batch 里多几条几乎不加。线上新实例在模块加载时装配内核（本地请求里 9–15 ms），是否计入请求的 `cpuTime` 由线上 `assemble` 与 `noop` 的差判断。
